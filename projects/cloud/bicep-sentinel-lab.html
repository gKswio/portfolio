Deploying Microsoft Sentinel with Bicep

A hands-on lab using Bicep to deploy a security monitoring stack in Azure — a Log Analytics Workspace, Microsoft Sentinel onboarding, and a Threat Intelligence data connector — version-controlled in an Azure DevOps repo.

Azure CLI Bicep VS Code Azure DevOps Microsoft Sentinel

1. Environment Setup

Azure Subscription

Created a free Azure subscription as the base for the lab.

Local Tooling

Installed the Azure CLI and Bicep CLI on Windows via winget:

winget install -e --id Microsoft.AzureCLI
az bicep install

Authentication

Registered MFA on the tenant and authenticated the CLI:

az login --tenant <tenant-id>

Version Control: Azure DevOps

Rather than deploying ad hoc, I set up a proper Git-backed workflow: created an Azure DevOps organization and a private project (bicep-learning), initialized a repo, cloned it locally via VS Code's "Clone in VS Code" integration, and installed the official Bicep VS Code extension for syntax highlighting and validation.

2. Building the Sentinel Stack

Log Analytics Workspace + Sentinel Onboarding

Microsoft Sentinel runs on top of a Log Analytics Workspace, so the first resource creates the workspace and the second onboards Sentinel onto it:

param location string = resourceGroup().location
param workspaceName string = 'law-${uniqueString(resourceGroup().id)}'

resource logAnalytics 'Microsoft.OperationalInsights/workspaces@2022-10-01' = {
  name: workspaceName
  location: location
  properties: {
    sku: {
      name: 'PerGB2018'
    }
    retentionInDays: 30
  }
}

resource sentinelOnboarding 'Microsoft.SecurityInsights/onboardingStates@2023-02-01' = {
  scope: logAnalytics
  name: 'default'
  properties: {}
}

output workspaceName string = logAnalytics.name
output workspaceId string = logAnalytics.id

The scope: logAnalytics line tells Bicep that the Sentinel resource depends on the workspace — deployment order is resolved automatically from that reference, with no manual sequencing needed.

Required resource providers were registered ahead of deployment:

az provider register --namespace Microsoft.OperationsManagement
az provider register --namespace Microsoft.SecurityInsights
az group create --name rg-test --location northeurope
az deployment group create --resource-group rg-test --template-file sentinel.bicep
✓

Result: provisioningState: Succeeded

3. Adding a Data Connector

To complete the stack, I added a Threat Intelligence data connector on top of Sentinel:

resource threatIntelConnector 'Microsoft.SecurityInsights/dataConnectors@2023-02-01' = {
  scope: logAnalytics
  name: 'ThreatIntelligenceConnector'
  kind: 'ThreatIntelligence'
  properties: {
    tenantId: subscription().tenantId
    tipLookbackPeriod: '2026-01-01T00:00:00Z'
    dataTypes: {
      indicators: {
        state: 'Enabled'
      }
    }
  }
  dependsOn: [
    sentinelOnboarding
  ]
}

Here dependsOn is set explicitly, since the connector references the workspace indirectly through Sentinel rather than owning it directly.

✓

Result: deployment succeeded, with a clean three-level dependency chain.

Log Analytics Workspace → Sentinel Onboarding → Threat Intelligence Connector

4. Cleanup

Every resource created during this lab was deployed into an isolated, disposable resource group and torn down immediately after verification:

az group delete --name rg-test

Zero cost throughout — confirmed via Cost Management, which showed no charges reported for the billing period.

What This Demonstrates

  • Writing and iterating on Bicep templates with proper parameterization and outputs
  • Understanding and using both implicit (scope) and explicit (dependsOn) resource dependencies
  • Git-based IaC workflow: local edits → commit → push → CLI deployment, tracked in Azure DevOps
